# 구조

## 왜 이렇게 나눴나

처음에는 전부 네이티브(Kotlin + Compose)였습니다. 그런데 실제로 써 보니
**고칠 때마다 온 가족이 파일을 받아 다시 설치**해야 했습니다. 하루에 몇 번 고치는
동안에는 이게 가장 큰 비용이었습니다.

그래서 자주 바뀌는 것(화면·규칙)을 기기 밖으로 뺐습니다.

```
   개발자                      GitHub                        가족 기기
 ─────────                  ──────────                    ────────────
 git push  ──▶  Actions: 검사 ──▶ Pages 배포  ──▶  앱을 열면 최신 화면
                                                          │
                                                          ▼
                                          WebView 안의 웹앱 (화면·규칙)
                                                          │
                                          ┌───────────────┴───────────────┐
                                          ▼                               ▼
                                   네이티브 껍데기                  Firebase (저장)
                                   알림만 담당                    기기끼리 주고받기
```

세로로 나눈 기준은 하나입니다. **자주 바뀌는가.**

| | 바뀌는 빈도 | 그래서 |
|---|---|---|
| 화면·규칙 | 하루에 몇 번 | 웹으로 빼서 배포로 해결 |
| 알림 예약 | 거의 안 바뀜 | 네이티브에 남김 (브라우저가 못 하는 일) |
| 자료 | 계속 바뀜 | 클라우드에 두어 기기가 비어도 살아남음 |

---

## 웹앱 (`web/`)

프레임워크를 쓰지 않습니다. 상태가 바뀌면 화면을 다시 그리는 방식입니다.
화면이 몇 개 안 되고 판단이 `core.js` 에 모여 있어 이 정도면 충분합니다.

| 파일 | 하는 일 |
|---|---|
| `core.js` | 자료 구조, 통계, 동기화, 연결 코드, 알람 일정 계산 |
| `ui.js` | 작업자 화면, 관리자 4개 탭, 첫 설정, 설정 |
| `app.css` | 화면 서식 (밝은/어두운 배색) |
| `sw.js` | 서비스 워커 |

### 서비스 워커는 네트워크를 먼저 본다

보통 PWA 는 캐시를 먼저 봅니다. 여기서는 반대입니다.
목적이 **"배포하면 바로 반영"** 이라 캐시 우선은 맞지 않습니다.
캐시는 인터넷이 끊겼을 때만 쓰는 예비용입니다.

## 네이티브 껍데기 (`app/`)

의존성이 둘뿐입니다 — `core-ktx`, `activity`. Compose 도 네트워크 라이브러리도 없습니다.

| 파일 | 하는 일 |
|---|---|
| `MainActivity.kt` | WebView 를 띄우고 `HennyShell` 다리를 연다 |
| `notify/ScheduleStore.kt` | 웹이 넘겨준 알람 일정을 보관 |
| `notify/AlarmScheduler.kt` | "다음 하나"만 예약 |
| `notify/AlarmReceiver.kt` | 알람이 울렸을 때 |
| `notify/BootReceiver.kt` | 재부팅 후 재예약 |
| `notify/Notifications.kt` | 알림 채널과 표시 |

### HennyShell 다리

웹이 부를 수 있는 것들입니다.

| 함수 | 하는 일 |
|---|---|
| `setSchedule(json)` | 3일치 알람 일정을 넘긴다 |
| `legacyData()` | Compose 시절 파일을 넘긴다 (이관용) |
| `version()` | 앱 버전 |
| `canNotify()` / `requestNotify()` | 알림 권한 |
| `openNotificationSettings()` / `openAlarmSettings()` | 설정 화면 열기 |

껍데기가 없어도(그냥 브라우저로 열어도) 앱은 돕니다. 알림만 안 울립니다.

## 자료 모델

문서는 두 종류뿐입니다.

**계획 문서** — 관리자가 쓰고 작업자가 읽습니다.

```
plan = {
  schema, updatedAt,
  workers:     [{ id, name, updatedAt }]
  routines:    [{ id, workerId, title, days, dueMinute, points, active, order, updatedAt }]
  assignments: [{ id, workerId, title, date, dueMinute, points, updatedAt }]
  reminders:   [{ id, workerId, minute, text, onlyIfIncomplete, days, enabled, updatedAt }]
  deleted:     { id: 지운시각 }
}
```

**기록 문서** — 작업자당 하나. 그 작업자가 쓰고 관리자가 읽습니다.

```
progress = {
  schema, workerId, updatedAt,
  days:    { "2026-08-20": { date, items: [{ taskId, title, doneAt, points }], updatedAt } }
  archive: [{ month, done, total, points }]
}
```

### 배점은 체크한 순간에 박힌다

`items[].points` 는 체크할 때의 값을 복사해 둡니다. 나중에 관리자가 배점을 바꿔도
이미 쌓인 마일리지가 흔들리지 않습니다.

### 오래된 날짜는 접는다

150일이 지난 날짜는 월별 합계(`archive`)로 접습니다. 문서가 계속 커지지 않게 하려는 것입니다.
누적 마일리지는 접힌 합계에도 남아 있어 끊기지 않습니다.

## 동기화

거의 실시간으로 맞되, 무료 한도를 낭비하지 않는 것이 목표입니다.

| 언제 | 무엇을 하나 |
|---|---|
| 앱을 열 때 | 곧바로 전체 동기화 |
| 화면이 켜져 있는 동안 | **15초마다 변경 여부만 확인**, 달라졌을 때만 전체를 받음 |
| 체크했을 때 | 2초 모았다가 올림 (연타를 한 번으로 묶음) |
| 화면에서 나갈 때 | 확인 루프 중단 + 미뤄둔 업로드 마무리 |
| 새로고침 버튼 | 작업자·관리자 화면 위쪽 |

### 값싸게 확인하기

Firebase 는 문서 안의 값 하나만 따로 읽을 수 있습니다.

```
https://…/henny/<팀>/plan/updatedAt.json   →   1787234013682
```

수십 바이트입니다. 그래서 15초마다 돌려도 거의 공짜입니다.
로컬보다 크면 그때만 전체를 내려받습니다.

값 하나만 읽는 기능이 없는 백엔드(JSONBin, 직접 주소)는 문서를 통째로 받아야 하므로
확인 주기를 **60초**로 늘려 잡습니다.

화면이 꺼지면 루프가 멈춥니다. 배터리와 데이터를 백그라운드에서 축내지 않습니다.

### 계획 문서는 항목 단위로 합친다

관리자가 여럿일 수 있습니다. 문서 전체의 시각만 보고 늦게 올린 쪽을 택하면,
**그사이 다른 관리자가 더한 작업이 통째로 사라집니다.**

그래서 항목마다 `updatedAt` 을 둡니다.

- 같은 id 가 양쪽에 있으면 → **나중에 고친 쪽**
- 한쪽에만 있으면 → **그대로 남김**
- 지운 표시(`deleted[id]`)가 항목의 `updatedAt` 보다 나중이면 → **지움**

지운 표시가 없으면 상대가 아직 들고 있던 항목이 합칠 때 되살아납니다. 그래서
삭제도 기록으로 남깁니다. 90일이 지나면 정리합니다.

`updatedAt` 은 **내용이 실제로 바뀐 항목에만** 찍습니다. 안 그러면 손대지 않은 항목이
매번 최신이 되어 다른 관리자의 수정을 밀어냅니다.

### 기록 문서는 부딪히지 않는다

기록 문서는 쓰는 사람이 한 명뿐입니다. 날짜별로 나뉘어 있어 합치기도 단순합니다 —
같은 날짜면 나중에 고친 쪽을 택합니다.

## 연결 코드

`HENNY2:` + base64url(JSON) 형태입니다. 안에는 저장소 접속 정보와 문서 주소가 들어 있습니다.

| 코드 | 담긴 것 | 쓰임 |
|---|---|---|
| 작업자 연결 코드 | 그 작업자의 기록 문서 주소 하나 | 작업자 기기 연결 |
| 관리자 코드 | 모든 문서 주소 | 관리자 추가, 기기 복구 |

### 저장 경로는 절대 새로 만들지 않는다

`provision()` 은 이미 쓰던 경로가 있으면 **반드시 그대로 다시 씁니다.**

예전에 여기서 자료를 잃은 적이 있습니다. 관리자 기기를 재설치하면 경로가 비어 있어
새 팀 키를 만들었고, 그때까지 쌓인 자료가 통째로 고아가 됐습니다.
지금은 이 규칙을 [검사로 못 박아](../tools/test_core.mjs) 두었습니다.

## 예전 앱에서 옮겨오기

Compose 시절 앱은 `filesDir/henny/*.json` 에 저장했고, 지금은 WebView 의 localStorage 에
저장합니다. 자리가 달라서 덮어 설치하면 화면이 빈 채로 뜹니다.

파일은 지워지지 않고 그대로 있으므로, 웹이 처음 열릴 때 한 번 읽어 옮깁니다
(`legacyData()` → `importLegacy()`). 자료 구조가 그때와 같아 그대로 넣으면 됩니다.

읽기만 합니다. 옮긴 뒤에도 파일을 지우지 않습니다.
이미 이 기기에서 쓰던 자료가 있으면 건드리지 않습니다 — 덮어쓰면 최신 기록이
옛 파일로 되돌아갑니다.

## 알려진 제약

- **방금 배정한 임시 작업**은 작업자가 앱을 연 뒤에야 알람에 잡힙니다.
  알람은 기기 안에 미리 예약해 두는 방식이라 그렇습니다.
  아침 알림이 매일 앱을 열게 하므로 실제 영향은 작습니다.
- **첫 실행에 인터넷이 없으면** 웹앱을 못 받아옵니다. 안내 화면을 대신 띄웁니다.
  한 번 받아 두면 그 뒤로는 캐시로 열립니다.
